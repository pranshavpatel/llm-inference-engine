# Phase 6 paired L40S backend run

The project owner returned the full one-command VM archive,
[`source.zip`](source.zip), SHA-256
`5c91d7bce1f24e99bbdd21a4ca3721f8b0ab2a1216e343aa17131b088d79c442`.
It records engine commit `701494f9d0f106b18c0855aa01c971b2bb7dc7b2`,
PyTorch `2.13.0+cu132`, FlashInfer `0.6.18.post1`, and an NVIDIA L40S. The
tracked Git worktree was clean. Before each server, `nvidia-smi` listed only
the display process, not another compute workload. Both readiness logs show
the pinned Qwen2.5-1.5B-Instruct model, 292 KV blocks, a 128 MiB KV pool, and
the intended reference or FlashInfer decode backend. Both used the same BF16
checkpoint, 16-token pages, 64-token context, and 16 active sequences.

The saved plan used identical independently seeded Poisson traces for both
backends: 1/2/4/6/10/16 offered requests/s, three 60-second repetitions per
rate, 20-second bounded drain, 256 client workers, and fixed 16-token outputs
with EOS ignored. All 36 replays passed trace and record validation. The
locally regenerated `report-sweep` JSON matched the archived report as parsed
data. Every run passed the predeclared p99 client send-lag gate of 50 ms; the
largest observed run p99 was below 1.8 ms. Every completed request had usage
and the required `length` finish with 16 completion tokens.

The compact [`summary.json`](summary.json), generated by
[`phase6_compare_summary.py`](../../scripts/phase6_compare_summary.py),
separates completion within the 60-second offered window from completion in
drain. The archive retains all raw traces, replays, environment records,
server logs, and the VM-generated report. The browsable `report/` copy is
included here.

At 4 requests/s, the reference path's median-of-run p50 TTFT was about 2.3×
the FlashInfer path's under this protocol. At 6, the reference queue grew:
238 completions landed in drain and median first-half versus second-half
TTFT rose from 4.04 to 10.32 seconds. FlashInfer had only 15 drain
completions at 6 and median TTFT stayed near 83–88 ms across the two halves.
At 10, the reference path had 654 failures (529 HTTP 429 and 125 drain
timeouts), while FlashInfer had none, although its median-of-run p99 TTFT was
1.31 seconds. At 16, both paths overloaded: reference had 1,746 failures and
FlashInfer 465, with rising queue delay. These high-rate points must not be
called sustainable capacity.

The two backends did **not** produce the same long greedy text: all 4,468
requests completed by both paths had differing 16-token output strings.
This extends the earlier BF16 full-model numerical-parity limitation. The
two-token functional smoke matched, and both backends satisfied the fixed
length/token accounting policy, but exact sequence parity is not established.
FlashInfer remains opt-in and reference gather remains the default.

This is a controlled **diagnostic** comparison, not a scored p99 frontier or
SLO-goodput claim. Each low-rate repetition has too few completions for a
strong p99 estimate; full-run throughput includes drain; the sample is one
VM session with the reference server run first. The generated-token strings
also differ even when output length is fixed. The data supports an observed
same-host latency and backlog improvement under this workload, not a
universal speedup or an exact-output replacement guarantee.
